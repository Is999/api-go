# 开发扩展指南

本文档用于新增 `api` 前台业务能力时快速对齐代码、文档、缓存和测试边界。

## 新增 HTTP 模块

1. 在 `internal/handler/{domain}/routes.go` 实现 `RouteSpecs`，路由规格单处声明 method、path、RouteMeta、接口文档、安全链路、访问日志降噪和 handler。
2. 在 `internal/handler/routes.go` 文件末尾的 `builtinRouteModuleSpecs` 增加模块规格。
3. 运行 `go test ./internal/bootstrap ./internal/handler`，确认真实路由、契约派生和默认注册名称不冲突。
4. 在 `internal/handler/shared/route_meta.go` 补 `RouteMeta`，别名使用 `domain.resource.action`，访问边界必须声明为 `public`、`auth` 或 `internal`。
5. 路由别名被 `RouteMeta`、`RouteSecurityPolicies`、鉴权事件或测试复用时，先在 `internal/routealias` 增加常量。
6. 需要登录态的路由必须走 `AuthMiddleware`；公开路由必须写清 token 校验边界。
7. 高频探针路由需要降噪时在 `RouteSpecs` 设置 `SkipAccessLog`，不要在 access log 中间件另维护路径白名单。
8. 内网运维路由必须使用 `internal` 安全链路，并在 `RouteSecurityPolicies` 中显式空策略，避免前台签名加密规则误拦运维调用。
9. 同步补 `docs/site/接口文档`，格式遵循接口文档统一规范；测试会校验文档包含真实路由路径。
10. 新增或修改安全字段后，通过 `DefaultRouteSecurityManifest()` 复核 alias、method、path、chain 和字段策略，再同步 `docs/site/route_security_manifest.json` 和前端同名 route policy。

## 签名与加密轻量策略

- `RouteSecurityPolicies` 必须按路由显式声明字段级策略；未知路由不默认参与签名或加密。
- `RequestSign` 和 `ResponseSign` 只列关键字段，禁止使用 `*` 对请求体、响应 `data`、大结构体或分页列表整体签名。
- 请求加密头 `X-Cipher` 只能声明 `RequestCipher` 允许解密的字段列表，禁止使用 `cipher` 整包加密；响应 `ResponseCipher` 只能声明 `data` 下的字段路径，禁止使用 `cipher` 整包加密。
- 单个接口参与签名或加密的字段最多 8 个；普通字段最大 4KB，`json:` 小对象最大 8KB。
- 安全中间件读取请求体最多 64KB；更大的业务负载必须绕开安全中间件解析路径，走专用上传、异步任务或拆分字段。
- 字段路径优先覆盖 token、金额、订单号、手机号、邮箱、二次校验字段等重要数据；普通展示字段、大列表和统计集合不默认签名或加密。
- 使用 `json:` 前缀前必须确认字段值很小且确实需要整体序列化；大对象、大数组和分页结果不得使用 `json:` 做整体加密。
- 新增或修改安全策略时必须同步接口文档 `### 安全字段` 表，写清请求签名、请求加密、响应签名和响应加密字段；没有敏感字段时明确说明不参与签名或加密。
- 安全链路失败必须使用细分业务码，禁止把 AppID、秘钥、验签、解密、响应加密和安全字段超限全部退回通用认证失败。
- 前端安全策略以 `internal/handler/route_security_manifest.go:DefaultRouteSecurityManifest` 为同步依据，路由 method/path/chain 来自模块 `RouteSpecs`，字段名称和顺序必须与后端清单一致；不在清单内的字段不得由前端自行加入签名或加密。
- `docs/site/route_security_manifest.json` 是前台工程同步快照，未知路由必须返回空策略，禁止默认全量签名或整包加密；同步流程见 `前端安全清单同步.md`。
- 修改签名串、`X-Cipher` 编码或字段数量边界时，必须同步 `internal/security/testdata/security_vectors.json` 和前端同名测试向量。

## 业务码与多语言

- 新增业务码先在 `common/codes/resp_code.go` 声明常量，再在 `common/codes/contract.go:defaultCodeSpecs` 维护 HTTP 状态、成功标识和默认文案 key；`IsSuccess`、`HTTPStatus`、`MessageByCode` 均从该契约派生。
- 新增默认文案 key 必须同步 `common/i18n/locales/active.zh-CN.json` 和 `common/i18n/locales/active.en-US.json`；`go test ./common/codes ./common/i18n` 会校验业务码契约、语言包和运行时映射一致。

## 运行期配置

- 启动期配置会执行基础校验：`app_id` 必填，`jwt_secret` 不能过短，Redis 地址和连接池必须有效，启用 Collector 时必须配置 Kafka broker 和业务 Topic。
- 雪花 ID 使用 `github.com/bwmarrin/snowflake`；生产多实例默认通过 `snowflake.redis` 从 Redis 共享租约池自动分配 `0-1023` node_id。同一套 `api/admin` 部署使用同一 `snowflake.redis.scope`，业务唯一域由调用方传入的 `NextID(namespace)` 决定，例如用户表统一使用 `user`，充值和提现订单可分别使用独立 namespace。
- `snowflake.redis.namespaces.<namespace>.node_count` 可限制单业务 namespace 的 node_id 池大小；未配置时使用完整 `0-1023`，当前 `user` 配置为 `10` 表示只竞争 `0-9` 这 10 个 node_id。所有会调用同一 `NextID(namespace)` 的服务必须保持该配置一致。
- 高吞吐业务可在 `snowflake.segment.namespaces` 按 namespace 启用 Redis Segment 本地号段；未配置的业务仍走雪花。Segment 每次只向 Redis `INCRBY` 申请一段本地缓存，不做 per-ID Redis 队列；进程崩溃可能产生未使用号段空洞，但不会产生重复 ID。
- Segment 适合订单号等唯一性优先的业务，不保留雪花时间位和 worker 位语义；`step` 和 `prefetch_threshold` 必须按业务峰值压测设置，避免过小造成 Redis 频繁申请，过大造成故障时空洞过多。
- `snowflake.worker_id` 仅用于手工强管控场景；启用 `snowflake.redis.enabled=true` 时不能同时配置 `worker_id`，避免静态配置覆盖自动分配。
- 雪花配置属于启动期配置，热加载变更只会标记为需重启，不会在线切换当前进程的 ID 生成器；某个业务 namespace 的 Redis 租约丢失后，当前进程只会停止该业务继续发号，避免重复 ID。
- 业务用户注册和登录先按登录请求身份类型路由到 `user_identity_username/user_identity_email/user_identity_phone/user_identity_oauth` 四张登录身份索引表。`username` 表保存 `identity_value`，`email/phone` 表只保存 HMAC `identity_hash`，`oauth` 表保存大小写敏感的 `provider/identity_value`；四张表都保存 `user_id/user_shard_no/user_route_shard_count`，用于保证登录身份唯一并为后续按量拆分物理用户表提供定位信息。
- 登录身份索引固定按身份类型拆成四张物理表，不再按身份哈希动态拆表；新增身份类型必须先评估唯一性、表规模、登录路由和回填方案，再新增对应物理表与模型路由。
- `user.route_shard_count` 控制新增用户默认物理表数量，仅支持 `1/2/4/8/16/32/64/128/256/512/1024`，当前样例配置保持 `1` 写入单表 `user`。未来拆表时先按主键游标分批回填四张登录身份索引表，再按 `user_shard_no` 范围搬迁到表后缀为范围起点的物理表，例如 2 表阶段 `user_0000/user_0512`，4 表阶段 `user_0000/user_0256/user_0512/user_0768`，最后按批更新索引表用户路由，不允许登录链路扫描所有用户分表。
- `user.route_shard_count` 属于启动期写入路由配置，热加载只会标记为需重启；提升档位必须在目标表就绪、索引回填完成后统一重启所有会写 `user` 的 api/admin 实例。
- `user_shard_no` 必须固定由 `idgen.ShardNo(user_id)` 生成；模型层会拒绝用户分片值不一致的数据。后续迁移或后台任务只能通过对应身份表的 `user_route_shard_count` 定位物理用户表，不能按表名猜测完整分片范围。
- 从 `1 -> 2 -> 4 -> 8 -> ... -> 1024` 扩容时允许按用户批次混合路由；批量复制和切换路由之间必须校验并补偿并发更新，身份索引未全量回填前不得提升新增用户默认物理表数量。
- `Mode=pro/prod/production` 会执行生产硬校验：`jwt_secret` 和 `ops.config_reload_token` 不能使用占位值，运维令牌必须达到最小长度，登录限流必须启用，Redis TLS 不能跳过证书校验。
- 生产环境开放注册时必须启用 `auth.register_rate_limit`；所有启用的认证限流参数必须控制在启动校验允许范围内，避免超大窗口或超长锁定时间。
- Collector 正常链路只投递 Kafka；`collector.default_task.topic` 提供默认 Topic，`collector.tasks.<bizType>.topic` 可按业务类型覆盖。
- `security.secret_key` 未配置时走普通请求链路；一旦配置，启动期会校验 `app_id`、版本唯一性、稳定/灰度版本引用、链路开关和 AES/RSA 材料。
- `sign_status`、`crypto_status` 只能为 `0` 或 `1`；启用签名或加密时必须配置用户 RSA 公钥和服务端 RSA 私钥，启用加密时还必须配置 AES KEY 与 IV。
- `security.secret_key` 的同一材料字段只能配置明文或 `*_ref` 之一；生产环境启用灰度秘钥时必须配置 `gray_salt`。
- `config_files.runtime` 只合并 `internal/bootstrap/configload/runtimefile:sectionSpecs` 声明的运行期配置段；新增外部运行期段时同步该规格、runtime 文件结构和合并测试。
- 业务读取运行期配置优先声明 `SysConfigKey`，再使用 `SysConfigLogic.GetBool`、`GetInt`、`GetString`、`GetFloat`、`GetObject` 或 `GetArray` 类型化读取。
- `GetCachedValue(uuid)` 仅用于确实需要动态 uuid 的场景。
- `sys_config` 表名固定无 `api_` 前缀，Redis 业务 Key 模板使用 `common/rediskeys` 中的 `config_uuid:%s`，真实 Key 统一通过 `AppScopedKey/AppRedisKey` 生成 `app:{app_id}:config_uuid:{uuid}`，和后台同 app_id 的配置缓存保持一致。
- 缓存缺失由 redsync 分布式锁保护回源，业务侧不要绕过逻辑层直接拼 Redis Key 或自行查表。
- 配置变更后的缓存刷新优先使用 `RenewByKey(key)`，动态 uuid 场景使用 `RenewByUUID(uuid)`；不要在线扫描高基数 Redis Key。
- 配置热加载 HTTP 接口属于内网运维能力，只注册 `/internal/system/...` 路由，必须携带 `X-Ops-Token` 和运维 HMAC 签名，生产环境需要配置 `ops.config_reload_token`。
- `ops.config_reload_allowed_ips` 只能在内网来源上进一步收窄访问范围，不能用于放行公网 IP。
- `ops.config_reload_allowed_ips` 配置非法 IP/CIDR 或公网 IP/CIDR 时会启动失败。
- 生产网关或 Ingress 必须拒绝公网转发 `/internal/` 路径；应用层会拒绝转发头中的公网来源。

## 认证与限流

- JWT 必须包含 `jti` 和当前服务 `app_id`；鉴权时会校验 token、Redis session、用户状态和 AppID 一致性。
- Redis session TTL 不超过 JWT 过期时间；刷新 token 会创建新 `jti`、写入用户 jti 索引并删除原 session，原 session 删除失败时必须回滚新 session。
- 鉴权成功会 best-effort 补齐用户 jti 索引，确保批量失效依赖的索引完整。
- 退出登录只删除当前 token 对应的 session；禁用用户、重置密码或风控封禁时使用 `AuthLogic.InvalidateUserSessions` 按 ZSET 索引精确失效全部 session。
- 登录入口使用 `auth.login_rate_limit` 按 IP 和用户名两个维度计数。
- 注册入口使用 `auth.register_rate_limit` 按 IP 计数，生产示例默认关闭注册。
- 注册、登录、刷新、退出、登录态鉴权失败、限流和用户全量失效会 best-effort 投递 `auth.security` 认证风控事件。
- 认证风控事件只包含用户 ID、脱敏用户名/IP/session 哈希、trace、route、app_id、动作和原因，禁止写入密码、token、明文用户名或明文 IP。
- 限流 Redis Key 必须继续使用 `common/rediskeys` 中的精确模板，不允许用通配扫描清理。

## Collector Kafka 模式

- 前台 API Collector 只负责把结构化业务事件写入 Kafka，不在请求链路内落 DB 或写 Redis。
- 新增 bizType 时配置 `collector.tasks.<bizType>.topic`，并保证 payload 是合法 JSON；未单独配置时走 `collector.default_task.topic`。
- 内置认证风控事件 bizType 为 `auth.security`，API 侧负责投递 Kafka 并统计 `api_collector_kafka_publish_events_total{result}`；动作和原因先维护 `internal/infra/collectorx/auth_security.go` 的契约源，细分安全指标由下游消费侧统计。
- Kafka 写入使用同步 ACK；投递失败会返回错误并触发 Lark 告警钩子，调用方按业务容忍度决定是否阻断主流程。
- Collector 事件 payload 不包含密码、token、明文用户名或明文 IP。

## 组件生命周期

- MySQL、Redis 等启动期核心组件先在 `internal/bootstrap/components:DefaultSpecs` 声明来源，再统一注册到 `svc.ComponentRegistry`。
- `/api/ready` 只遍历组件注册表执行探测；新增核心依赖时不要在 `HealthLogic` 里临时追加检查分支。
- 服务停止时按组件注册顺序反向释放资源；新增组件必须同时评估 `Check` 和 `Close` 是否需要配置。
- 组件注册清单从 `components.DefaultSpecs` 派生；新增组件时不要另写一份文档清单。
- 新增内置轻量运行时扩展时先维护能力归属包的 `RuntimeRegistrySpecs`；新增 Collector bizType 时同步 `collector.tasks` Topic 配置、调用入口和注册清单。

## 数据与缓存命名

- 前台业务表默认使用清晰业务名，例如用户表为 `user`；只有特殊业务边界需要时才使用业务前缀。
- 全局运行期配置只使用 `sys_config`，不得新增 `api_sys_config`。
- Redis Key 必须集中定义在 `common/rediskeys`，禁止业务代码临时拼高基数通配 Key。
- 涉及大表或高频查询时，必须先确认索引、批量边界、超时和库压力。

## 必补检查

- 新增默认路由或运行时入口后执行 `go test ./internal/bootstrap ./internal/handler`。
- 新增或修改签名、加密字段后执行 `go test ./internal/handler`，确认路由安全清单、接口文档和字段级策略一致。
- 更新前端安全策略时先比对 `docs/site/route_security_manifest.json`，未知路由不得回退到 `*` 或 `cipher`。
- 修改签名串或 `X-Cipher` 编码后执行 `go test ./internal/security`，并在前端执行对应 security vector 单测。
- 涉及 sys_config、缓存锁或 Collector 时执行对应包测试。
- 后端改动完成后优先执行 `go test ./...`，最后执行 `git diff --check`。
