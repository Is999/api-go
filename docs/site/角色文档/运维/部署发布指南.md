# 部署发布指南

## 目标

本文约束 `api` 前台 API 的上线、配置、数据库版本登记和生产观测流程。后台管理和运营任务由 `admin` 承担。

## 部署前检查

上线前确认：

1. 已执行 `make ci`，或至少完成 `gofmt`、`go test ./...`、`go build ./cmd/api`、`go build ./cmd/migrate`。
2. 已通过 `make migrate-dry-run MIGRATE_CONFIG=...` 确认数据库迁移计划。
3. `sys_config` 表使用未加前缀的表名；前台业务表默认使用清晰业务名。
4. `etc/config.yaml` 已从环境模板生成，并配置强随机 `app_id`、`app_key`、`jwt_secret`；`trusted_proxies` 仅包含实际 LB/Ingress 地址或网段；已有敏感数据后变更 `app_key` 必须配套密钥版本迁移、历史回填和回滚方案，不能直接热切。
5. `snowflake.redis.enabled=true` 已启用，且同一套 `api/admin` 部署使用同一 `snowflake.redis.scope`；同一业务唯一域必须使用相同 `NextID(namespace)` 和 `snowflake.redis.namespaces.<namespace>.node_count`，当前 `user` 使用 10 个 node_id。仅手工强管控场景允许改用全局唯一的 `snowflake.worker_id`；如启用 `snowflake.segment`，确认对应 namespace 的 `scope/step/prefetch_threshold` 已压测。
6. 生产 `Mode=pro/prod/production` 已启用登录限流；开放注册时已启用注册限流。
7. 已配置 `ops.config_reload_token` 和独立 `internal_server`；跨主机监听使用明确私网 IP 与 mTLS，运维请求携带随机 nonce，Redis 防重放链路可用。
8. `/api/live`、`/api/ready`、`/api/metrics` 在目标环境按内网或网关白名单可访问。
9. `docs/site/route_security_manifest.json` 与前端安全清单同步，未知路由不默认进入全量签名或整包加密。
10. 如启用 Lark 运行异常告警，已配置 `alert.lark.webhook_url_ref` 或 `alert.lark.webhook_url`，并确认群机器人签名密钥来源正确。

## 构建

```bash
make ci
make package VERSION=20260605
```

没有 `make` 的环境可等价执行：

```bash
gofmt -w $(find . -name '*.go' -not -path './vendor/*')
go test ./...
go build -o bin/api ./cmd/api
go build -o bin/api-migrate ./cmd/migrate
```

发布产物至少包含：

- `bin/api`
- `bin/api-migrate`
- `dist/api-<version>.tar.gz`
- `etc/config.yaml`
- 必要的证书、密钥和运行期配置文件

仓库提供的部署模板：

- `deploy/docker/Dockerfile`
- `deploy/systemd/api.service`
- `deploy/integration/docker-compose.yml`

## 数据库版本治理

上线工具应先执行 dry-run，再执行 up：

```bash
make migrate-dry-run MIGRATE_CONFIG=./etc/config.yaml
make migrate-up MIGRATE_CONFIG=./etc/config.yaml
```

当前基线迁移包括：

| version | name | asset |
| --- | --- | --- |
| `202606220001` | `create_user` | `user_schema.sql.tmpl` |
| `202606220002` | `create_sys_config` | `sys_config_schema.sql.tmpl` |
| `202606220003` | `create_user_identity_username` | `user_identity_username_schema.sql.tmpl` |
| `202606220004` | `create_user_identity_email` | `user_identity_email_schema.sql.tmpl` |
| `202606220005` | `create_user_identity_phone` | `user_identity_phone_schema.sql.tmpl` |
| `202606220006` | `create_user_identity_oauth` | `user_identity_oauth_schema.sql.tmpl` |

API 迁移使用独立版本号段，避免和同库 admin 迁移版本冲突。

运维约束：

- 新环境按 `DefaultMigrations()` 顺序执行未登记版本，并写入 `version`、`name`、`asset`、`checksum`、`applied_at`。
- 已登记版本的 SQL 内容不得修改；需要变更时新增更高版本迁移。
- 新增迁移只维护 `internal/database/migrations.go:defaultMigrationSpecs`，不要在执行器或命令入口重复登记。
- SQL 资产按稳定表或业务域收口，不为少量字段、种子或配置修复新增 `sync_*`、`*_seed_*`、`*_repair_*` 碎片化迁移。
- 带显式自增主键 `id` 的 seed 行必须按 `id` 递增排列，不能按业务相似性插入到中间。
- 发布前运行 `go test ./internal/database` 校验迁移清单和 checksum。
- admin 与 API 迁移命令共用 MySQL 命名锁 `app:schema-migration`；并发迁移最多等待 60 秒，超时后直接终止当前发布任务。
- 迁移连接池的 `mysql.max_open_conns` 必须为 `0` 或至少为 `2`，因为命名锁和迁移执行各需要一条连接。
- `sys_config` 是 admin/API 共用运行期配置表，保持不加前缀。
- `user` 初始 DDL 已包含雪花 ID、`shard_no`、联系方式密文、联系方式 HMAC 查询哈希、认证版本 `auth_version` 和分片游标索引；`user_identity_username/user_identity_email/user_identity_phone/user_identity_oauth` 是按身份类型拆分的登录身份索引，其中邮箱和手机号身份只保存 HMAC `identity_hash`。当前项目未上线，认证版本直接收口到基线 DDL；若目标库已存在旧表，必须先新增 `auth_version bigint unsigned NOT NULL DEFAULT 1`，再启用新版登录态。历史数据需要按 `user.id` 游标分批回填安全字段和身份索引，避免一次性 `INSERT ... SELECT` 压住业务库。

业务用户按量拆表运行边界：

1. `shard_no = CRC32(十进制 user.id)%1024` 固定不变，身份目录只保存稳定的 `user_id/user_shard_no`。
2. 主线默认 `user.route_shard_count=1`，运行时支持 `1/2/4/.../1024`，Admin/API 必须保持一致。
3. 主线不包含生产迁移命令；应用内拆表使用 `table-sharding/app-table-sharding`，Proxy 拆表使用 `table-sharding/shardingsphere-proxy-alternative`。
4. 目标表、全量复制、增量追平和一致性校验完成前，禁止修改路由配置或 Proxy 规则。
5. 切换时短暂排队写请求并停止所有直写进程，禁止旧、新配置实例同时写库。
6. 切换失败时保持旧路由；目标已经接收新写后不得直接切回过期源数据。

具体迁移命令、权限、校验、清理和回滚边界以所选方案分支的 Admin 路由规范为准。

详细规则见 [数据库迁移治理](角色文档/运维/数据库迁移治理.md)。

## 启动期硬校验

服务启动会在进入运行态前校验以下风险：

- `jwt_secret` 长度过短。
- Redis 地址为空或连接池大小无效。
- 雪花 Redis 租约参数不安全，Segment 号段参数非法，或手工 `snowflake.worker_id` 缺失、越界。
- `user.route_shard_count` 不在 `1/2/4/.../1024` 允许档位内。
- 认证密码最小长度低于安全下限。
- 登录/注册限流窗口、次数或锁定时间超过可控范围。
- Collector 未启用，或 `collector.tasks.auth.security.topic` 不是 `api_collector_auth_security_events`。
- 运维白名单配置公网 IP/CIDR。
- 生产环境使用占位密钥、未配置运维令牌、关闭登录限流或跳过 Redis TLS 证书校验。

## 运行

```bash
./bin/api -f ./etc/config.yaml
```

配置热加载只刷新运行期配置，不重建 HTTP 监听、MySQL、Redis、OTLP 等启动期连接。启动期配置变化会在热加载状态中标记为需重启。
`alert.lark` 发送端配置也属于启动期依赖，热加载变更只记录需重启，不在线替换 webhook 或签名密钥。

## 观测与告警

发布后至少确认：

- `/api/live` 返回成功。
- `/api/ready` 中 MySQL、Redis、Collector 等组件状态正常。
- `/api/metrics` 可被 Prometheus 从内网抓取，公网不可直接访问。
- 日志中可通过 `trace_id`、`route`、`uid`、`app_id` 关联一次请求。
- ID 生成指标 `api_idgen_generated_total{biz_type,strategy,result}` 有基线数据；启用 Segment 时同时观察 `api_idgen_segment_remaining{biz_type}`、`api_idgen_segment_allocations_total{biz_type,result}` 和 `api_idgen_snowflake_lease_events_total{biz_type,event}`。
- Collector Kafka 投递指标 `api_collector_kafka_publish_events_total{result}` 有基线数据。
- 如启用 `alert.lark`，启动失败、平滑停止失败、配置热加载失败和 Collector 投递失败会发送 Lark 运行异常卡片。
- 认证安全细分指标由 Admin Kafka 消费侧按 `auth.security` 的 `action/reason/app_id/category` 聚合；`route` 仅保留在事件中辅助排障。
- Prometheus 可加载 `docs/prometheus/api-alerts.yml`，并按生产基线调整阈值。
- Grafana 可导入 `docs/grafana/api-dashboard.json` 观察 API 基线和 Collector 投递状态。

详细 PromQL 参考 [认证安全指标与告警](角色文档/后端开发/认证安全指标与告警.md)。

## 发布流程

容器或进程托管平台的终止宽限期不得低于 30 秒。服务收到信号后最多等待 5 秒排空 HTTP 请求，再为基础设施关闭保留 20 秒，并在 29 秒触发框架强退保护。

1. 合并代码并完成测试。
2. 执行数据库迁移，确认 `schema_migrations` 中新版本和 checksum 登记成功。
3. 发布新二进制和配置。
4. 确认 `/api/ready` 正常。
5. 对登录、刷新 token、用户信息、系统配置读取执行低风险冒烟。
6. 若启用签名或加密，使用前端安全清单覆盖至少一个签名接口和一个加密接口。
7. 观察 10 到 30 分钟认证安全指标、错误日志和 Redis session 写入。

## 回滚

1. 摘除异常实例或回退流量。
2. 恢复上一版本二进制和配置。
3. 确认 `/api/ready`、登录、刷新 token 和 Redis session 正常。
4. 如果本次包含数据库迁移，按迁移单确认是否需要反向脚本或补偿任务。
5. 观察 `security_config`、`token`、`auth` 分类指标，确认异常恢复到基线。
