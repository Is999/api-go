# 数据库迁移治理

## 适用范围

本文说明 `api` 仓库内置迁移工具的执行边界、命令选择和发布步骤。迁移入口是 `cmd/migrate`，迁移清单来自 `internal/database.defaultMigrationSpecs`，SQL 资产位于 `internal/database/assets/`，执行结果登记到 `schema_migrations`。

迁移只管理 `api` 自己的前台业务库表。后台管理库、任务调度库、历史数据回填、用户表物理拆分和跨库补偿任务必须单独制定方案，不能直接套用本文命令。

## 版本表与状态

`schema_migrations` 记录已成功执行的迁移版本，字段包含 `version`、`name`、`asset`、`checksum` 和 `applied_at`。迁移工具会按 `version` 升序处理迁移，已登记版本不会重复执行。

命令输出中的 `STATUS` 含义：

| 状态 | 含义 | 处理方式 |
| --- | --- | --- |
| `applied` | 版本已登记且 checksum 匹配，本次不会再执行 SQL | 正常状态 |
| `pending` | 版本未登记，且当前命令只预览计划 | 先评审 SQL、备份，再执行 `migrate-up` |
| `executed` | 本轮已执行 SQL 并登记版本 | 执行后复核表结构、关键数据和 `schema_migrations` |
| `blocked` | 被 bootstrap-only 或 destructive 安全策略拦截 | 不要绕过，先确认目标库和迁移类型 |

`api` 迁移对已登记版本执行严格 checksum 校验。只要已登记版本的 SQL checksum 与当前资产不一致，`status`、`dry-run` 和 `up` 都会报错；历史迁移不得修改，需要变更时新增更高版本迁移。

## 命令入口

所有命令在 `api` 目录执行，`MIGRATE_CONFIG` 必须指向目标环境的实际配置文件：

```bash
cd api
```

| 命令 | 实际动作 | 是否写业务库 | 适用场景 | 安全边界 |
| --- | --- | --- | --- | --- |
| `make build-tools` | 构建 `bin/api-migrate` | 否 | 发布打包前确认迁移二进制可构建 | 不连接数据库 |
| `make migrate-status MIGRATE_CONFIG=./etc/config.yaml` | 连接 MySQL，读取 `schema_migrations`，输出当前版本状态 | 否 | 日常巡检、发布前确认 applied/pending/checksum | 只读；版本表不存在时按未执行迁移展示 |
| `make migrate-dry-run MIGRATE_CONFIG=./etc/config.yaml` | 读取版本表并输出执行计划、拦截原因 | 否 | 每次上线前必须执行 | 只读；不能替代 SQL 评审、备份和回滚方案 |
| `make migrate-up MIGRATE_CONFIG=./etc/config.yaml` | 创建版本表，执行未登记且未被拦截的迁移，登记版本 | 是 | 新环境或已有库执行普通增量迁移 | 执行前必须完成 dry-run、备份和计划确认 |
| `make integration-test` | 启动本地集成 MySQL，运行迁移集成测试 | 否，不碰业务库 | 修改迁移执行器、拦截规则或 SQL 资产后验证 | 依赖 Docker；结束后用 `make integration-env-down` 清理本地容器和卷 |

等价二进制命令：

```bash
bin/api-migrate -f ./etc/config.yaml -action=status
bin/api-migrate -f ./etc/config.yaml -action=dry-run
bin/api-migrate -f ./etc/config.yaml -action=up
bin/api-migrate -version
```

`cmd/migrate` 预留了 `-allow-bootstrap` 和 `-allow-destructive` 参数，但当前 Makefile 没有暴露 bootstrap 命令。只有未来明确新增 bootstrap-only 或 destructive 迁移，并完成单独评审、备份和回滚方案后，才允许人工使用这些参数。

## 该执行哪个命令

| 场景 | 执行命令 | 说明 |
| --- | --- | --- |
| 只想确认当前库迁移状态 | `migrate-status` | 只读，可快速发现 pending 或 checksum 不一致 |
| 新环境初始化当前普通基线 | `migrate-status` → `migrate-dry-run` → `migrate-up` → `migrate-status` | 当前基线不是 bootstrap-only，使用普通 up |
| 已有环境上线普通增量迁移 | `migrate-status` → `migrate-dry-run` → 备份 → `migrate-up` → `migrate-status` | 这是生产标准路径 |
| dry-run 出现 `blocked` | 停止执行 | 说明迁移被标记为高风险，必须重新评审 |
| status 出现 checksum 不一致 | 暂停发布 | 历史资产已变更，必须恢复原资产或新增正向迁移 |
| 迁移包含 DROP、TRUNCATE、DELETE 或字段删除 | 单独评审 | 必须有备份、回滚或补偿方案，不走普通快速上线 |

## 已有库上线步骤

1. 确认配置文件指向目标库，尤其是 MySQL 地址、库名、用户名和生产环境标识。
2. 构建迁移工具：

```bash
make build-tools
```

3. 查看当前状态：

```bash
make migrate-status MIGRATE_CONFIG=./etc/config.yaml
```

4. 预览上线计划：

```bash
make migrate-dry-run MIGRATE_CONFIG=./etc/config.yaml
```

5. 只有 dry-run 输出符合预期、没有 unknown blocked、没有 checksum 报错时，才做数据库备份并执行：

```bash
make migrate-up MIGRATE_CONFIG=./etc/config.yaml
```

6. 执行后复核：

```bash
make migrate-status MIGRATE_CONFIG=./etc/config.yaml
```

7. 核对 `schema_migrations` 中的 `version/name/asset/checksum/applied_at`，并按迁移内容抽查表结构和关键数据。

## 当前基线

当前基线迁移：

| version | name | asset |
| --- | --- | --- |
| `202606220001` | `create_user` | `user_schema.sql.tmpl` |
| `202606220002` | `create_sys_config` | `sys_config_schema.sql.tmpl` |
| `202606220003` | `create_user_identity_username` | `user_identity_username_schema.sql.tmpl` |
| `202606220004` | `create_user_identity_email` | `user_identity_email_schema.sql.tmpl` |
| `202606220005` | `create_user_identity_phone` | `user_identity_phone_schema.sql.tmpl` |
| `202606220006` | `create_user_identity_oauth` | `user_identity_oauth_schema.sql.tmpl` |

`sys_config` 保持不加前缀，供 admin/API 共用运行期配置。`user` 初始 DDL 已包含雪花 ID、`shard_no`、联系方式密文、联系方式 HMAC 查询哈希和分片游标索引；`user_identity_username/user_identity_email/user_identity_phone/user_identity_oauth` 四张登录身份索引表分别使用独立 SQL 资产和迁移版本，负责 `username/email/phone/oauth` 唯一和后续物理用户表定位，其中邮箱和手机号身份表只保存 HMAC `identity_hash`。物理拆分用户表时必须先全量回填安全字段和这些索引表，再按批复制、校验、切换 `user_route_shard_count` 并补偿并发更新。

新增业务 DDL 时，把 `*.sql.tmpl` 放入 `internal/database/assets`，并只在 `internal/database/migrations.go:defaultMigrationSpecs` 增加版本、名称和资产名；`DefaultMigrations()`、checksum 和资产覆盖测试会从该规格派生。

SQL 资产按稳定表或业务域收口。少量字段、种子或配置修复不要拆成 `sync_*`、`*_seed_*`、`*_repair_*` 这类碎片化迁移；确实需要新增迁移时，必须代表独立 DDL 或补偿边界，并在发布单说明原因、数据范围和回滚方式。

维护带显式 `id` 的 seed SQL 时，新增行必须按自增主键递增顺序落位；即使业务语义相近，也不要把高 id 行插入到相似模块附近。`go test ./internal/database` 会检查同一资产同一表内的 seed id 顺序。

## 失败处理

- `status` / `dry-run` 失败：通常是配置、网络、账号权限、版本表读取异常或 checksum 不一致。先修复根因，不执行 `up`。
- `up` 被 `blocked` 拦截：不要加 `allow` 参数绕过。先确认迁移类型、目标库和回滚方案。
- `up` 执行 SQL 失败：停止发布，保留输出中的 `version/name/asset/statement`，核对已执行到哪条 SQL。
- MySQL DDL 可能隐式提交，不能完全依赖事务自动回滚。恢复方式以数据库备份、快照回滚或新增正向补偿迁移为准。
- 本工具没有 `down` 命令；已发布迁移需要回退时，必须新增更高版本的正向修复迁移或按备份恢复。

## 发布要求

上线前必须完成：

1. `make migrate-dry-run MIGRATE_CONFIG=...` 确认计划。
2. 核对 `checksum`，历史版本不得被修改。
3. 执行后核对 `schema_migrations` 登记版本。
4. 如新增 destructive 或 bootstrap-only 迁移，必须显式标记并单独准备回滚或补偿方案。
5. 迁移执行器或 SQL 资产发生变化时，执行 `go test ./internal/database`；涉及真实 MySQL 行为时补跑 `make integration-test`。

迁移执行器会按分号拆分 SQL，并跳过文件内 `BEGIN`、`COMMIT`、`ROLLBACK`、`START TRANSACTION`，不要求 MySQL DSN 开启 `multiStatements=true`。
